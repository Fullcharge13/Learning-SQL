# 레슨 쓰기 안내 (두억이와 SQL!)

레슨을 쓰는 일꾼은 **이 문서 + 설계서 §6 표의 그 장 줄 + 예시 `data/lessons/ch1.js`**만 읽으면 된다. 판정 번호(R21 등)는 근거 표시일 뿐이다.
숫자 한도는 모두 `tests/content.js` 맨 위 상수에서 옮겨 왔다. 둘이 어긋나면 점검기가 맞고, 이 문서를 고친다.

학습자는 SQL을 처음 보는 사람이고, **타자를 치지 않는다.** 모든 문제는 누르기(보기 고르기·빈자리 칩·줄 놓기·카드 조립)로 푼다.

## 1. 파일 모양

`data/lessons/chN.js` 하나가 장 하나다.

```js
export const CHAPTER = { id: N, title: "장 제목" };          // 제목은 설계 §6 표 그대로
export const LESSONS = [ /* N-1 … N-5. N-5가 장 평가(isExam: true) */ ];
export const TEMPLATES = [ /* 매일 도전 틀 N-T1 … 2~5개, 6절 */ ];
```

- **장마다 레슨 5개, 5번째가 장 평가**다(판정 R21). id는 파일 안 순서대로 `N-1` … `N-5`, `chapter: N`. `isExam: true`는 `N-5`에만 둔다.
- 레슨 하나:

```js
{ id: "N-k", chapter: N, title, goal, summary: ["…", "…", "…"], isExam?: true, updated?: "v0.2",
  cards: [ { say, sql? } ],                 // 설명 카드 1~2장
  items: [ 터치 문제들 → build 문제들 → check 1개 ] }
```

- `updated`는 이미 나간 레슨을 보강했을 때만 그 판 이름(`"v0.2"`)을 적는다. 새 레슨에는 두지 않는다.
- 모르는 칸 이름은 오류다(오타 막기). 문제 차례는 반드시 **터치 문제(choice·blank·order) → build → check 하나(맨 끝)**.

### 1-1. 설명 카드 `{ say, sql? }`

- `say`: 두억이 말풍선(140자, 줄바꿈 가능). `sql`: 보여 줄 SQL. **앱이 실행해서 결과 표를 그린다**(손으로 쓴 표 없음). 50행이 넘으면 앞 50행과 「… 외 N행」.
- 리아의 `code`·`out`·`files`·`stdin`·`show_only`·`chart` 칸은 없다(쓰면 「old field」 오류). 다른 데이터베이스 SQL은 `sql` 대신 1-1-1절의 `show`·`dialect`.
- 말풍선 아래에 SQL과 표가 나온다. 말풍선에서는 「아래 SQL」이라고 가리킨다.

### 1-1-1. 보기 전용 비교 카드 `{ say, show, dialect }` (판정 R30, 16장)

- 다른 데이터베이스의 문법을 **보이기만** 하는 설명 카드다. `show`는 SQL 글자, `dialect`는 `"MySQL"`·`"PostgreSQL"` 중 하나(`src/lessondata.js`의 `DIALECTS`, 대소문자까지 같게).
- 화면은 `dialect` 이름표 + 「보기 전용이에요. 이 장터에서는 돌지 않는 SQL이에요.」 + 점선 코드 상자를 그린다. **실행하지 않아** 결과 표·실행 단추가 없다(`src/ui/dom.js` `cardExample`).
- 한 카드에 `sql`과 `show`를 함께 두지 않는다. `dialect`는 `show`와만 쓴다(`validateLesson`).
- 점검기: `show`는 `grammar`·`engine-guard`·실행 검사를 받지 않는다(MySQL·PostgreSQL 함수 이름을 써도 됨). **한 줄 38칸(SQL_COLS)과 `readonly`는 그대로** 받는다.
- `show`의 문법은 공식 문서로 확인하고 장 머리 주석에 출처를 적는다. 말풍선에는 이 장터(SQLite)의 무엇과 짝인지 말로 짚는다.
- 레슨 카드 1~2장 한도 안에서 쓴다. 문제에는 `show`의 SQL을 `code`·보기 SQL로 넣을 수 없으니(실행됨) 「PostgreSQL의 TO_CHAR가 하는 일은?」처럼 글자 보기로 묻는다.

### 1-2. 문제 종류와 칸

| type | 꼭 있어야 할 칸 | 있어도 되는 칸 |
|---|---|---|
| `choice` | `concept, q, options, answer, explain` | `id, code, tables` |
| `check` (이해도 확인, 레슨 맨 끝 1개) | choice와 같음 | choice와 같음 |
| `blank` | `concept, q, code, chips, answer, explain` | `id` |
| `order` | `concept, q, lines, explain` | `id, expect` |
| `build` (카드 조립) | `type, id, concept, q, cards, extra, tables, hints, explain` | `need, allowEmpty` |

- **choice / check**
  - `options` 3~4개. **전부 글자**이거나 **전부 `{ sql }`**(결과 표 보기)이고, 섞지 않는다. `answer`는 0부터 센 정답 번호(화면이 섞는다).
  - 글자 보기는 한국어 설명이거나 SQL 한 줄이다. 화면 글꼴은 `src/textkind.js`가 정한다.
    - 글자 상수 `'…'` 밖에 한글이 없고 SQL 기호·대문자 낱말이 있으면 고정폭 글꼴.
    - SQL 낱말로 시작하면 `AS` 뒤 별칭·따옴표 이름의 한글도 빼고 본다(R32).
    - 그 밖의 한글 문장은 보통 글꼴.
  - `{ sql }` 보기: 앱이 각 SQL을 돌려 **앞 5행짜리 작은 표**로 그린다. 보기끼리 화면에서 달라 보여야 한다(열 이름, 앞 5행, 전체 행 수 중 하나 이상).
    - 보기 SQL의 셈 열에는 별칭을 붙인다(`COUNT(*) AS n`, `MIN(age) AS age_value`). 별칭이 없으면 열 머리에 `COUNT(*)`·`MIN(age)`가 보여 값을 안 보고 함수 이름만으로 고를 수 있다(8장). 보기끼리 같은 별칭을 쓰고, 함수 뜻과 어긋나는 이름(`SUM(price) AS avg_price`)은 피한다.
  - `code`(선택): 문제 위에 보일 SQL. `tables`(선택): 「쓸 표 보기」 단추에 보일 표 이름들.
  - **장 평가(N-5)의 결과 표 객관식에는 `tables`를 두지 않는다**(점검기 `shape`). 「쓸 표 보기」가 정답 보기와 똑같은 표를 보여 줘서 짝 맞추기가 되기 때문이다. 연습 레슨(N-1~N-4)에서는 둬도 된다.
- **blank**: `code`에 빈자리 `___`이 **정확히 하나**(학습자 글에서도 「빈자리」라 부른다, 9절). `chips` 3~4개, `answer`는 정답 칩 번호. 오답 칩을 넣은 SQL은 **오류이거나 정답과 다른 결과**여야 한다(규칙 `blank-unique`). 줄바꿈 `\n` 가능.
- **order**: `lines` 3~6줄을 **정답 순서대로** 저장한다(화면이 섞는다). 줄마다 한 줄 글자, 같은 줄 두 번 금지. 이은 SQL이 돌아야 하고, **다른 모든 순서는 오류이거나 다른 결과**여야 한다(규칙 `order-unique`).
  - `expect`(선택, 판정 R22)는 정답 화면에 「실행 결과」로 보일 글자다. **첫 줄은 열 이름, 다음 줄부터 행 하나에 한 줄, 칸은 ` | `로 잇는다.** NULL은 `NULL`, 실수는 소수 넷째 자리까지. 점검기가 실제 실행 결과와 견주어 다르면 오류(실제 글자를 알려 준다).
  - 예: `expect: "name | price\n산삼 | 120\n갓 | 110"`. 결과가 길면 화면이 지저분하니 5행 안팎일 때만 쓴다.
- **build**: 7절.

### 1-3. `concept`

`data/concepts.js`의 id. 그 개념의 `chapter`가 레슨의 장보다 뒤면 안 된다. 앞 장 개념을 다시 써도 된다(10장 조인 문제에 `where` 등). 장마다 쓸 id는 이미 17장 모두 들어 있다. 꼭 새 개념이 필요하면 **더하기만** 하고(id는 학습자 저장에 남음) 그 장 번호를 단다.

| build 힌트 | **정확히 2개** | `validateLesson`(점검기가 `shape`로 알림) |

- 폭은 한글 등 넓은 글자를 2칸으로 센다. 탭 문자 금지(공백 스페이스로).
- 제목·목표·문제·해설·말풍선·힌트에는 한글이 들어가야 한다. 제목·목표·문제·힌트는 한 줄.
- `summary`는 정확히 3줄.
- 문제 `id`는 장을 넘어서도 겹치면 안 된다. build의 id는 `N-k-b1`, `N-k-b2`처럼 쓴다(ch1 예시).
- 데이터를 바꾸는 낱말(INSERT·UPDATE·DELETE·CREATE·DROP·ALTER 등)은 SQL에도 **한국어 글에도** 쓰지 않는다(설계 D11, 규칙 `readonly`).
- 화면에 보이는 SQL은 모두 실행기 검사를 통과해야 한다: **`SELECT` 또는 `WITH`로 시작하는 문장 하나**(규칙 `engine-guard`).

## 3. 터치 문제 쓰는 법

- **`ORDER BY`가 없는 결과에는 정해진 행 차례가 없다.**
  - 데이터베이스는 그때그때 편한 차례로 행을 내놓는다. 그래서 「첫 행」·「맨 위 행」·「마지막 행」·「두 번째 줄」을 묻거나 말하지 않는다. 보기·해설·말풍선 모두 그렇다(「첫 행만 보여 줘」 같은 오답 보기도 쓰지 않는다).
  - 행은 **값으로 가리킨다**: 이름이나 번호로 「국밥 행」, 「item_id가 11인 행」(ch1 1-2 「국밥 행과 price 열이 만나는 칸」).
  - 행의 차례는 5장에서 `ORDER BY`와 함께 처음 가르친다. 그 뒤로도 차례를 말할 때는 그 SQL에 `ORDER BY`가 있어야 하고, 동점이 없게 고유 열까지 정렬한다(7절 `stable-order`).
  - 열의 차례(「맨 앞 열 item_id」)는 표마다 정해져 있으니 말해도 된다.
- **객관식은 말로 묻는다.** 결과 표 보기(`{ sql }`)를 쓸 때 정답 보기의 SQL을 그대로 `code`로 보여 주고 「이 SQL의 결과로 알맞은 표는?」이라고 묻지 않는다. 실행기를 못 받은 휴대폰에서는 보기 표를 그릴 수 없다. 그때 보기 하나가 문제 SQL과 같으면, 정답이 드러나지 않게 **모든 보기가 「표를 불러오지 못했어요」**로 바뀌어 찍을 수밖에 없다.
  - 좋은 예: 「가게(shops) 표를 통째로 보여 준 결과는 어느 것일까요?」 + 보기 `{ sql }` 셋. 학습자는 열 이름과 값을 보고 고른다.
  - 「값이 비싼 물건 3개의 이름」처럼 말로 조건을 주고 결과 표를 고르게 해도 된다.
  - 매일 도전 틀(6절)은 엔진 구조상 늘 정답 SQL을 보여 주는 모양이고, 따로 막아 두었다.
- **점검기가 실제로 돌려 보는 객관식**
  - `code` + 글자 보기: `code`가 오류면 정답 보기에 「오류」가 들어가야 하고, 오류 없이 돌면 정답 보기에 「오류」가 없어야 한다.
  - `code`의 결과가 값 하나(1행 1열)면, 그 값과 같은 글자의 보기는 정답 하나뿐이어야 한다.
  - `q`에 「몇 행」·「몇 줄」이 있으면 실제 행 수를 말하는 보기(`8행`)가 정답 하나뿐이어야 한다.
  - `code` 없이 글자 보기가 모두 SQL이고 `q`에 「오류가 나는」 또는 「오류 없이」가 있으면, 보기를 모두 돌려 정답을 확인한다.
  - `{ sql }` 보기에 `code`가 있으면 `code`의 결과가 정답 보기의 표와만 같아야 한다. 단, 위 규칙대로 같은 SQL을 `code`로 쓰지 않는다.
- 점검기가 못 보는 것(「열이 몇 개」, 「국밥의 값은」 등)은 직접 돌려 확인한다. 임시 확인은 `tests/content.js`의 `openEngine()`으로 SQL을 돌려 보면 된다(8절).
- 오답 보기는 그 장에서 학습자가 실제로 하는 실수로 만든다: 비슷한 표 이름(`orders`·`order_items`·`items`), 같은 행의 옆 열 값(값 대신 재고), 행 수와 열 수 혼동, 차례가 바뀐 낱말.
- 정답이 첫 보기에 몰려도 괜찮다(화면이 섞음).
- blank 오답 칩·order 줄·글자 보기도 **그 장까지 배운 낱말**만 쓴다(5절). 점검기가 오답 칩의 낱말도 본다.
- blank의 칩은 앱이 실행하지 않고 번호로 채점한다. 오답 칩이 `SELECT`로 시작하지 않는 SQL을 만들어도 레슨에서는 괜찮다. 틀은 다르다(6절).

## 4. 설명 카드 쓰는 법

- 레슨의 새 개념을 카드에서 **처음 보여 주고**, 문제는 그 뒤에 낸다. 카드에 없던 낱말·모양을 문제에서 처음 쓰지 않는다.
- 낯선 말은 처음 나올 때 한 번 풀어 쓴다(「행은 가로 한 줄」). 용어를 한 번 정하면 바꾸지 않는다.
- 카드 `sql`은 실제 결과 표가 같이 보이므로, 말풍선에서 표의 무엇을 볼지 짚어 준다(「맨 앞 열 item_id는 …」). 행은 차례가 아니라 값으로 가리킨다(3절 첫 항목).
- 한 장 안에서도 **카드에 나온 다음에** 문제로 낸다. 1-1 문제가 1-3 카드에서 처음 가르치는 것(여러 줄 SQL, 차례가 틀린 SQL의 오류)을 쓰면 안 된다. 문제가 아직 카드에 없던 표를 보아야 풀린다면, 카드에서 그 표를 보여 주거나 문제에 `tables`를 달아 「쓸 표 보기」로 펼쳐 볼 수 있게 한다.
- 행이 아주 많은 표(`orders` 591행, `order_items` 1,241행)도 카드에서 보여 줄 수 있다. 앞 50행만 그려진다.

## 5. 장마다 쓸 수 있는 낱말 (`data/grammar.js`)

**그 장까지 배운 낱말만 쓴다**(누적). 점검기 규칙 `grammar`가 모든 SQL 칸(카드·`code`·보기·칩·줄·카드 더미·틀)을 본다. 표·열·별칭 이름, 숫자, 글자 상수 `'…'` 안은 보지 않는다.

| 장 | 새 낱말 | 설계 §6 밖에서 더한 것(판정 R23) |
|---|---|---|
| 1 | `SELECT` `FROM` (`*`는 기호라 검사 안 함) | |
| 2 | `AS`, 계산 기호 `+ - /` (`%`는 2장 심화 전용, 아래) | |

- **2장 `*`의 두 뜻**: `SELECT` 바로 뒤의 `*`는 「모든 열」이고, 값 사이의 `*`는 곱하기다(`price * 2`). 1장은 `*`의 뜻을 묻는 문제에 「곱하기」를 오답 보기로 썼고 「그건 2장에서」라고 미뤄 두었다. 그래서 2장 카드는 두 뜻을 **나란히** 보여 준다. 예: `SELECT *` 결과와 `SELECT name, price * 2` 결과를 잇달아 보여 주고, 「자리가 다르면 뜻이 달라요」라고 짚는다.
- **별칭(`AS`)은 영어 이름을 쓴다**(판정 R32): `price * 2 AS double_price`.
  - 한글 별칭(`AS 값`, `AS "두 배 값"`)은 SQL에 한글이 섞인다. 열 이름은 영어 + 화면 한글 뜻이라는 약속(설계 D10)에서도 벗어난다.
  - 화면은 SQL 낱말로 시작하는 보기를 한글 별칭이 있어도 코드로 보이게 해 두었다(`src/textkind.js`). 그래도 영어 별칭을 쓴다.
  - 별칭 이름은 소문자와 밑줄로, 뜻이 드러나게 쓴다(`double_price`, `total_qty`).
- **정수 나눗셈**: SQLite는 정수끼리 나누면 소수점 아래를 버린다(수육 `25 / 2` = 12). MySQL은 12.5를 낸다. 2장은 「이 장터에서는」으로만 가르쳤으니, **9장 `CAST`에서 데이터베이스마다 다르다는 것을 짚는다**.
- **`%`(나머지)는 2장 심화(2-A2) 전용이다**(v0.2, `ADVANCED_GRAMMAR[2]`). 본 과정 레슨·매일 도전 틀에서 글자 상수 밖에 `%`를 쓰면 점검기 `grammar`가 잡는다. LIKE 무늬 안의 `%`(`'%방망이'`)와 글 보기의 「50%」는 상관없다. 13절.
- 굵은 낱말은 설계 §6 「배우는 것」 칸에 이름이 없지만 그 장에서 가르치기로 한 것이다(판정 R23). 쓰는 장의 카드에서 꼭 한 번 보여 주고 쓴다.
- **어느 장에서도 안 되는 것**(`UNTAUGHT`): `RIGHT` `FULL` `CROSS` `NATURAL` `USING` `INTERSECT` `EXCEPT` `RECURSIVE` `VALUES`, `RANGE` `GROUPS` `WINDOW` `FILTER` `NTILE` `FIRST_VALUE` `LAST_VALUE` 등 다른 창 함수, `GLOB` `REGEXP` `COLLATE` `NULLS` `ISNULL` `NOTNULL`, `GROUP_CONCAT` `IIF` `INSTR` `PRINTF` `DATETIME` 등 함수, `RANDOM` `CURRENT_DATE` 같은 실행마다 바뀌는 것, `ROWID`. 목록에 없는 함수를 부르면 「가르치지 않는 함수」 오류. `NULLIF`는 6장 심화 전용(13절)이라 본 과정에서는 쓰지 않는다.
- 그 밖의 금지: 글자 값에 큰따옴표(`"먹거리"` → `'먹거리'`), `==`(→ `=`), `'now'`(날짜는 글자로 적음).
- `GRAMMAR`에 낱말을 더하거나 옮겨야 하면 일을 멈추고 묻는다(다른 장 레슨이 걸릴 수 있음).

## 6. 매일 도전 틀 `TEMPLATES`

「오늘의 도전」 터치 문제 2개는 끝낸 장의 틀에 값을 바꿔 끼워 매일 새로 만든다. 조립 문제 1개는 끝낸 레슨의 build를 그대로 쓴다(틀로 만들지 않음). 장마다 **2~5개**. 엔진은 `src/template.js`, 점검은 같은 `node tests/content.js`(틀이 있으면 늘 검사, 규칙 `templates`).

```js
export const TEMPLATES = [
  { id: "1-T1", concept: "table", type: "choice",
    q: "이 SQL의 결과로 알맞은 표는?",
    sql: "SELECT * FROM {T}",                         // 화면에 보이는 정답 SQL
    wrong: ["SELECT * FROM {U}", "SELECT FROM {T}"],  // 오답 SQL 2~3개 → 보기는 실제 결과 표(오류면 「오류가 나요」)
    vars: { T: ["shops", "items", "customers"], U: ["orders", "order_items"] },
    explain: "FROM 뒤에 적힌 표 {T} 그대로가 정답이에요. …" },
  { id: "1-T2", concept: "selectall", type: "blank",
    q: "{T} 표의 모든 열이 나오게 빈자리를 채워 보세요.",
    sql: "SELECT ___ FROM {T}", chips: ["*", "FROM", "SELECT"], answer: 0,
    vars: { T: ["shops", "items", "customers", "orders", "order_items"] },
    explain: "모든 열은 * 하나로 말해요." },
];
```

- **칸**: choice는 `id concept type q sql wrong vars explain` + 선택 `tables`. blank는 `id concept type q sql chips answer vars explain`. 리아 시절의 `code`가 아니라 **`sql`**이다.
- **`id`**는 `N-T1`, `N-T2` …. 학습자 저장에 남으니 한 번 정하면 바꾸지 않는다.
- **`concept`**: 그 장 이하의 본 과정 개념.
- **`vars`** 1~6개
  - 이름은 대문자(`T`, `KIND`, `P_2`). 값은 목록 `[…]`(2~40개, 정수 또는 글자, 겹침 없음) 또는 `{ min, max }`(정수).
  - 글자 값에는 `' " \ { }`와 줄바꿈을 넣지 않는다(SQL `'{KIND}'` 안에 들어감).
  - 선언한 이름은 어딘가(q·sql·wrong·chips·explain)에 꼭 쓰고, 쓴 `{이름}`은 모두 선언한다.
  - 값은 서로 따로 뽑힌다. 두 값을 짝지을 수 없다(예: 표 이름과 그 한글 뜻을 따로 뽑으면 어긋난다). 짝이 필요하면 하나만 뽑고 문장에 영어 이름을 쓴다.
- **choice 틀**: 화면은 `sql`을 보여 주고 「결과로 알맞은 표는?」을 묻는다. 보기는 정답·오답 SQL을 실제로 돌린 결과 표다.
  - 보기 표끼리는 화면에서 달라야 한다. 기준은 sameTable이 다를 것(정답에 바깥 ORDER BY가 있을 때만 순서를 봄), 그리고 앞 5행·행 수가 다를 것.
  - **오류 난 오답 둘은 같은 「오류가 나요」라 겹친다.** 오류 오답은 하나까지만.
  - 같은 목록에서 뽑은 두 값이 같아지면 겹친다. 오답에는 정답과 **겹치지 않는 목록**을 쓰거나, 오류 오답을 쓴다(1-T1).
- **blank 틀**: `sql`에 `___` 하나. 오답 칩을 끼운 SQL은 오류이거나 다른 표여야 한다. **틀은 모든 칩을 실제로 실행하므로, 칩을 끼운 SQL도 `SELECT`/`WITH`로 시작해야 한다**(`engine-guard`). 그래서 첫 낱말 `___ * FROM …` 같은 틀은 쓸 수 없다.
- **씨앗 0~99를 모두 돌린다.**
  - 정답 SQL은 오류 없이 **1행 이상**이어야 한다.
  - 보기가 겹치면 같은 씨앗의 다음 시도로 값을 다시 뽑는다. **5번 안에** 안 겹쳐야 한다.
  - 점검 줄의 「다시 만든 것 n」이 크면 값 범위를 고친다.
  - 500ms가 넘으면 「느림」. 학습자 화면에서는 시간 초과가 「다시 시도」 화면이 된다(R28).
- 보이는 SQL(choice `sql`, blank의 정답 채운 SQL)은 한 줄 38칸. 값을 끼운 `q`(80자, 한 줄)·`explain`(160자)도 길이를 본다.
- **자리 표시 바로 뒤에 조사를 붙이지 않는다**: `{N}을`·`{T}이니`는 값에 따라 틀린다. `{N}개를`, `{T} 표에서`처럼 단위·명사를 붙인다.
- 순서가 있는 정답 SQL은 7절과 같이 고유 열로 끝까지 정렬한다(`ORDER BY price DESC, item_id`).

## 7. 카드 조립(build) 정답 규칙

```js
{ id: "1-1-b1", type: "build", concept: "selectall",
  q: "가게 목록을 전부 보여 줘",               // 과제(80자, 한 줄, 두억이에게 부탁하는 말투)
  cards: ["SELECT", "*", "FROM", "shops"],     // 정답 카드, 정답 순서대로. 공백 하나로 이으면 정답 SQL
  extra: ["items", "customers"],               // 헷갈림 카드 2~4장
  tables: ["shops"],                           // 「쓸 표 보기」. 정답이 쓰는 표는 모두 넣어야 함
  hints: ["무엇을 생각할지 한 문장", "필요한 SQL 낱말"],   // 정확히 2개(120자, 한 줄)
  need: ["…"],                                 // (선택) 꼭 써야 하는 카드 글자. cards 안에 있어야 함
  allowEmpty: true,                            // (선택) 일부러 0행인 정답일 때만
  explain: "…" }
```

- **힌트 4단계**(설계 §4-5): ① `hints[0]` 무엇을 생각할지 → ② `hints[1]` 필요한 SQL 낱말 → ③ 앱이 정답 카드 절반을 놓아 줌 → ④ 다음 카드 하나씩 놓아 줌. 그래서 손으로 쓰는 힌트는 2개뿐이다. ①은 답 카드를 그대로 불러 주지 않는다.
- **결과 비교 채점**: 조립한 SQL을 돌려 정답 SQL의 결과와 견준다(열 이름 대소문자 무시, 실수는 넷째 자리, `ORDER BY`가 있을 때만 순서). 결과가 같으면 다른 카드 차례도 정답이다.
- **조립 정답의 계산 열에는 별칭을 붙인다.** 채점은 열 이름까지 견주므로, 별칭이 없으면 앞뒤만 바꾼 바른 조립 `2 * price`가 정답 `price * 2`와 열 이름이 달라 오답이 된다(`AS double_price`처럼 붙이고 `need: ["AS"]`). 별칭 없이 쓰려면 앞뒤를 바꾸면 값이 달라지는 셈(`price - 5`)만 쓴다(2장).
- **`stable-order`(판정 R13)**: 순서가 있는 정답은 **고유한 열까지 `ORDER BY`**해서 동점의 차례가 바뀔 수 없게 한다.
  - 예: `ORDER BY price DESC, item_id`.
  - 점검기는 두 벌로 확인한다. 하나는 저장 순서를 거꾸로 한 데이터베이스이고, 다른 하나는 바깥 `ORDER BY`에 모든 열 번호를 오름·내림으로 덧붙인 판이다.
  - `GROUP BY` 결과를 줄 세울 때도 동점이 없게 둘째 기준을 단다.
  - `ORDER BY` 없는 `LIMIT`은 어떤 행이 나올지 정해지지 않아 쓰지 않는다.
- **번호와 이름으로 함께 묶기(판정 R46)**: 손님·물건·가게마다 묶을 때 이름만으로 묶지 않는다(`GROUP BY c.name` ✗). 이름은 겹칠 수 있으니 번호와 이름을 함께 쓴다: `GROUP BY c.customer_id, c.name`, `GROUP BY i.item_id, i.name`.
  - 지금 장터 데이터는 이름이 모두 달라 결과가 같지만, 이름으로 묶는 버릇을 들이지 않는다. 카드·`code`·보기·줄 놓기·틀 모두 같다.
  - 여러 열 `GROUP BY`는 11-3 첫 카드에서 처음 보여 준다(「이름이 같은 손님이 있을 수 있어 번호와 이름으로 함께 묶어요」). 조립에서는 `"i.item_id, i.name"` 구절 카드 한 장으로 둔다.
  - 번호 없이 값으로 묶는 것(마을·종류·값·가게 번호)은 그대로 된다.
- **50행 이하**: 정답 결과가 50행을 넘으면 비교 표가 잘린다. 조건이나 `LIMIT`(5장부터)으로 줄인다. 1~4장에서 표 전체를 고르는 정답은 `shops`(8행)·`items`(40행)만 된다.
- **`drop-one`**: 정답 카드 **어느 하나를 빼도** 오답이어야 한다. 빼도 결과가 같은 카드(쓸모없는 카드)는 넣지 않는다. 빼서 시간 초과가 나면 학습자 화면에서도 「너무 오래 걸려요」(오답)라 문제로 보지 않는다(R24).
- **`swap-extra`**
  - 헷갈림 카드는 정답 카드 **한 자리와 바꿔도** 오답이어야 한다.
  - **끼워 넣기는 앱이 막는다(판정 R48, 마지막 전체 검수).** 학습자가 정답 카드를 차례대로 모두 놓고 카드를 더 놓으면(정답의 상위 집합), 결과가 같아도 `judgeBuild`가 오답(`reason: "extra"`)으로 채점하고 두억이가 「정답 카드는 다 있는데, 카드가 하나 더 들어갔어요. 빼도 되는 카드를 찾아볼까요?」라고 말한다. 그래서 점검기는 끼워 넣기를 따로 돌리지 않는다. 상위 집합이 아닌 진짜 다른 답(`100 < price`처럼 카드가 다른 것)은 그대로 결과로 채점한다.
  - 데이터상 결과가 같아지는 헷갈림 카드는 「틀린 줄 알았는데 맞았다」를 만든다. 예: 그 데이터에서 `>`와 `>=`의 결과가 같은 경우. 점검기가 찾아 준다.
  - 표 별칭 자리(판정 R26·R33, R48로 정리): 표 이름 바로 뒤에 놓은 낱말(`FROM shops items`), LIKE 무늬(`FROM items '%방망이' WHERE …`), 글자 값(`FROM shops '먹거리' WHERE …`)을 SQLite는 **표 별칭**으로 읽어 결과가 정답과 같아진다. 예전에는 점검기가 낱말 카드만 예외(R26)로 두고 무늬·글자 값 카드를 피하게 했다(R33, 3·4장). **이제는 앱이 이런 조립을 상위 집합으로 보고 오답 처리(R48)하므로 이 자리 때문에 헷갈림 카드를 고르지 않아도 된다.** 3·4장의 지금 헷갈림 카드(`<>`·`=`·`IN`·표/열 이름)는 그대로 둔다.
  - **`+` 카드를 `*`·`-` 옆 헷갈림 카드로 쓰지 않는다.** `price * + 2`는 「+2」로 읽혀 `price * 2`와 같다(2장).
- **1~5장 조립의 길이 한도(4장)**: 더미 12장 − 헷갈림 2장 = 정답 카드는 **10장까지**다. `SELECT * FROM 표 WHERE`가 카드 5장이라 조건은 카드 5장 안이어야 한다.
  - 되는 것: `price BETWEEN 10 AND 20`(카드 5장), `name LIKE '%방망이%'`(카드 3장), `name NOT LIKE '…'`(카드 4장), 비교 하나(카드 3장).
  - 안 되는 것: 비교 둘을 `AND`·`OR`로 잇기(카드 7장), `shop_id IN ( 7 , 8 )`(카드 6장, 합 11장). 이런 것은 터치 문제로 가르친다. 5장 `ORDER BY`·`LIMIT` 조립도 이 한도를 먼저 센다.
  - 6장부터는 구절 카드(R38)로 이 한도가 풀린다. `WHERE` `age IS NULL` `AND` `kind = '사람'`이 카드 4장이라, 6~13장 작가는 AND·OR 조립을 넣을 수 있는 곳에 넣는다(판정 R34 메모).
- **카드 크기**
  - **1~5장: 카드 하나에 낱말·기호 하나**(`SELECT`, `*`, `,`, `price`, `>=`, `200`, `'먹거리'`).
  - **6~13장: 1~3토큰의 짧은 구절 카드를 쓸 수 있다(판정 R38).** 예: `stock IS NULL`, `stock IS NOT NULL`, `COALESCE(stock, 0)`, `price > 100`, `AND`, `AS total`. 함수 부르기 `COALESCE(stock, 0)`은 괄호까지 한 단위로 친다.
    - `SELECT`·`FROM`·`WHERE`(뒤 장의 `ORDER`·`BY`·`GROUP` 등 문장 뼈대 낱말도)는 **한 장씩** 둔다. 문장 차례를 놓는 것이 조립 연습의 몸통이다.
    - **`GROUP BY`·`ORDER BY`는 두 낱말이지만 6장부터 구절 카드 한 장(`"GROUP BY"`, `"ORDER BY"`)으로 친다(판정 R40).** 낱장 두 장(`"GROUP"`, `"BY"`)으로 쓰지 않는다. 8장 조립도 모두 한 장으로 맞췄다.
    - **10장부터 JOIN 카드**: 표와 별칭은 한 장(`"orders o"`, `"JOIN customers c"`), ON 조건은 30칸 안이면 `"ON oi.item_id = i.item_id"` 한 장, 넘으면 `"ON"`과 조건 두 장. 세 표 매출(`SELECT` + 셈·별칭 + `FROM` + 표 + JOIN·ON 두 쌍 + `WHERE` + 조건)이 이렇게 해서 10장에 들어간다. (표 이름 뒤에 끼운 낱말은 R48로 앱이 막는다.) 헷갈림 카드는 점이 든 이름(`shops.name`)이나 조건으로 쓰고, 낱말 하나뿐인 열 이름(`name`)은 SELECT 열 뒤에서 열 별칭이 되므로 쓰지 않는다. ON을 빠뜨린 모양(모든 짝)은 조립 정답으로 쓰지 않고 `COUNT(*)`로만 보인다(10장 머리 주석).
    - **12장부터 서브쿼리 카드**: 괄호는 낱장으로 두지 않고 여는 카드·닫는 카드에 붙인다(`"(SELECT AVG(price)"`, `"FROM items)"`, `"category = '공방')"`). 괄호 안 `WHERE`는 바깥처럼 한 장. 서브쿼리 전체가 30칸 안이면(`"(SELECT AVG(price) FROM items)"`) R42처럼 한 장으로 둘 수도 있으나, 괄호 자리를 놓는 연습이 빠져 12장은 쓰지 않았다. EXISTS 괄호 안은 `"(SELECT * FROM orders o"`와 짝 조건 한 장. **괄호 안 표에 없는 열 이름은 오류가 아니라 바깥 표의 열로 읽힌다**(`(SELECT item_id FROM shops …)`가 바깥 items.item_id를 씀). 헷갈림 카드·해설에 「열이 없어 단서」라고 쓰기 전에 돌려 본다.
    - **서브쿼리 경계 카드(판정 R44)**: 서브쿼리의 여는 카드 `(SELECT … FROM t x`(예: `"(SELECT * FROM orders o"`, `"(SELECT village, COUNT(*) AS n"`)와 닫는 절 카드 `… )`(예: `"GROUP BY village)"`, `"FROM items GROUP BY shop_id)"`)는 R42와 같은 뜻으로 구절 카드 한 단위로 친다(30칸 안). 13장 `WITH 이름 AS`도 한 장. **FROM 안 서브쿼리의 별칭은 닫는 카드에 붙인다**(`"GROUP BY customer_id) t"`): 별칭을 낱장으로 두면 SQLite는 별칭 없이도 돌아 빼도 정답이 된다(`drop-one`).
    - **3토큰을 넘는 카드(판정 R45, 10~13장)**: 구절 카드는 1~3토큰이 원칙이고(30칸 안), 3토큰을 넘어도 되는 것은 다음 다섯뿐이다.
      - (a) 표와 그 별칭: `"orders o"`, `"JOIN customers c"`, `"LEFT JOIN order_items oi"`
      - (b) ON 조건 하나: `"ON oi.item_id = i.item_id"`
      - (c) R44 서브쿼리 경계 카드: `"(SELECT * FROM orders o"`, `"HAVING COUNT(*) > 1)"`, `"AND age IS NOT NULL)"`, `"GROUP BY customer_id) t"`
      - (d) ON에 붙는 `AND 조건`: `"AND o.status = '취소'"`, `"AND oi.qty = 3"`
      - (e) 계산 열 하나와 그 별칭: `"oi.qty * i.price AS amount"`, `"SUM(oi.qty * i.price) AS sales"`
      - `IS NOT NULL`은 R38 예(`stock IS NOT NULL`)대로 비교 하나로 쳐서 `"o.order_id IS NOT NULL"`은 3토큰 조건 카드다.
      - 바깥 문장의 뼈대 낱말(`SELECT`·`FROM`·`WHERE`·`GROUP BY`·`HAVING`·`ORDER BY`·`UNION`)은 이 다섯에 섞지 않고 늘 제 카드에 둔다.
      - **이름 붙은 예외**: `"ORDER BY total DESC, shop_id"`(헷갈림 `"ORDER BY total, shop_id"`) 한 장(13-1-b1·13-2-b2·13-5-b1)은 더미 12장 한도 때문에 받아들였다. **선례로 삼지 않는다.**
    - **13장 UNION 조립**: 양쪽이 `SELECT … FROM …` 한 벌씩이라 WHERE를 넣으면 12장을 넘는다. WHERE 없는 두 표를 쌓고, WHERE가 든 UNION은 터치 문제로 보인다. 겹치는 행이 없는 데이터에서는 `UNION`과 `UNION ALL`을 헷갈림 짝으로 쓰지 않는다(결과가 같음).
    - 좋은 구절 카드는 학습자가 「이 덩어리를 여기 놓는다」고 뜻으로 말할 수 있는 한 단위다: 조건 하나(`age IS NULL`), 계산 열 하나(`COALESCE(stock, 0)`), 별칭(`AS stock_or_zero`), 잇는 말(`AND`·`OR`). 구절을 쪼개면 그 장에서 배울 모양(예: `IS NOT NULL`의 차례)을 연습하게 하고, 붙이면 더미 12장 안에 AND·OR와 열 이름이 들어간다. 무엇을 연습시킬지 보고 고른다.
    - **모든 카드는 여전히 쓸모가 있어야 한다(`drop-one`).** 구절 하나를 빼도 결과가 같으면 그 구절은 넣지 않는다.
    - 구절로 붙이면 엔진의 너그러운 읽기를 피하기도 한다: SQLite는 `stock NOT NULL`(IS 없이)도 받아서, `IS`·`NOT`·`NULL`을 낱장으로 두면 `IS`를 빼도 정답이 된다(6장). 낱장으로 두려면 `need: ["IS"]`를 단다.
  - **헷갈림 구절 카드**는 정답 구절과 모양이 거의 같고 결과만 달라야 한다. 바꿔 넣거나 끼워 넣으면 결과가 바뀌어야 한다(`swap-extra`).
    - 좋은 짝: `stock = NULL` ↔ `stock IS NULL`(0행), `COALESCE(stock, 1)` ↔ `COALESCE(stock, 0)`(빈칸이 1), `OR` ↔ `AND`(행 수가 달라짐), `COALESCE(stock, 0) = 0` ↔ `stock = 0`(빈칸까지 걸림).
    - 데이터상 결과가 같아지는 짝은 쓰지 않는다. 예: SQLite의 `stock IS 0`은 `stock = 0`과 같다.
    - 헷갈림 구절이 표 이름 바로 뒤에 끼워져 표 별칭으로 읽히는 것(R33)은 이제 앱이 막는다(R48: 정답 카드 + 남는 카드 = 오답). 바꿔 넣기(`swap-extra`)는 여전히 점검기가 모두 돌려 본다.
    - 한 장 폭 30칸은 그대로다. 긴 구절(`COALESCE(stock, 0) AS x`)은 둘로 나눈다.
  - **14장부터는 덩어리 카드**(`OVER (PARTITION BY shop_id`, `ORDER BY total DESC)`). 카드 하나는 30칸 이하.
    - **판정 R47(14~17장)**: 카드 더미 12장과 카드 폭 30칸은 14~17장에서도 그대로다. 실제 분석 SQL(세 표 JOIN + GROUP BY + 창 함수 등)이 더미에 들어가지 않으면 설명 카드·객관식·빈자리로 가르치고, **같은 모양의 조립**을 더 작은 표로 하나 둔다(13장 진짜 매출 → items 합계, 14장 가게마다 가장 잘 팔린 물건 → 가장 비싼 물건, 15장 손님별 누적 구매액 → 가게마다 사 모은 값). 해설에서 대표 문제와 같은 뼈대라고 알린다.
    - 14장부터는 바깥 문장의 덩어리 카드가 뼈대 낱말과 그 대상을 함께 담아도 된다: `SELECT * FROM ranked`, `WHERE rk = 1`, `FROM daily`. 창 함수가 없는 조립은 지금처럼 `SELECT`·`FROM`·`WHERE`를 한 장씩 둔다.
    - 창 함수 덩어리는 뜻으로 나눈다: `SUM(price) OVER`, `(ORDER BY price, item_id)`, `price - LAG(price) OVER`, `ROWS BETWEEN 2 PRECEDING`, `AND CURRENT ROW), 1) AS avg3`(15장). 줄 놓기(order) 한 줄은 휴대폰 폭 때문에 33칸 안으로 쓴다.
  - 같은 글자 카드가 두 장 필요하면 `cards`에 두 번 써도 된다. 단, 헷갈림 카드는 정답 카드·서로와 글자가 겹치면 안 된다.
- 표·열 이름 카드에는 화면이 한글 뜻을 작게 붙인다(`shops`/가게). `tables`에 그 문제의 표를 적어 두면 뜻을 그 표에서 먼저 찾는다.
- 카드 더미는 문제 `id`를 씨앗으로 섞는다. 섞은 결과에서 정답 카드가 정답 순서 그대로 보이면 점검기가 알린다. 그러면 `id`를 바꾼다.
- **`need`**: 결과는 같아도 그 장의 낱말을 꼭 쓰게 할 때. 예: 10장 `["JOIN"]`. 과제 문장에도 그 낱말을 쓰라고 적는다.
- 장 평가(N-5)는 1~4 레슨 build들의 개념을 모두 한 번 이상 다룬다(규칙 `exam-coverage`, build가 아닌 문제로 다뤄도 된다).

## 8. 장마다 넣을 것

- **장터 예**: 설계 §6 표의 「장터 예」를 그 장의 **대표 build 문제**로 넣는다. 그것을 가르치는 레슨에 한 번, 장 평가에 한 번 넣는다. 과제 문장을 거의 그대로 쓰고, 해설에서 대표 문제라고 알린다(ch1 「가게 목록을 전부 보여 줘」).
  - **5장 장터 예는 예외다(판정 R34)**: 「가장 비싼 물건 5개」(5-3-b1·5-5-b1) 정답 `SELECT * FROM items ORDER BY price DESC LIMIT 5`에는 둘째 기준 `item_id`가 없다. 다섯째(쇠솥 260)와 여섯째(놋그릇 190)가 동점이 아니어서 결과가 하나로 정해지고, `, item_id`를 더하면 카드 더미 12장 한도를 넘기 때문에 받아들인 예외다. **뒤 장에서 이것을 「둘째 기준 없이 LIMIT해도 된다」는 선례로 삼지 않는다.** 순서가 있는 정답은 7절 `stable-order`대로 고유 열까지 정렬한다.
  - **8-3-b1도 같은 예외다(판정 R43)**: 정답 `SELECT shop_id , SUM(price) AS total FROM items GROUP BY shop_id ORDER BY total DESC`에는 둘째 기준 `shop_id`가 없다. 가게 8곳의 값 합(1330·1100·232·209·116·95·64·35엽전)이 모두 달라 차례가 하나로 정해지고, `, shop_id`를 더하면 카드 더미 12장 한도를 넘기 때문에 받아들인 예외다. 해설에 「같은 합이 있을 수 있으면 shop_id를 둘째 기준으로 붙여요」를 적었다. **이것도 선례로 삼지 않는다.**
- **실무 한 줄**: 장 평가(N-5)의 **맨 끝 check 문제의 `explain` 끝 문장**을 「실무에서는 …」으로 쓴다. 장을 끝내며 마지막으로 보는 글이다.
  - 형식: 「실무에서는 이 표가 쇼핑몰의 ○○표에 해당해요」. 그 장에서 배운 것이 실제 일의 어디에 쓰이는지 한 문장으로.
  - 이 한 줄은 점검기가 확인하지 않는다. 검토 때 눈으로 본다.
- **장 평가 레슨**
  - 제목 「N장 평가」, 설명 카드 1장(정리 + 대표 SQL).
  - 문제 10~16개, build는 2절 한도까지. 그 장의 모든 개념을 고루 묻는다.
- **TEMPLATES** 2~5개(6절).

## 9. 말투와 용어

- **두억이**: 도깨비 장터에 사는 꼬마 도깨비. 장부 셈이 특기인 척하지만 사실 배우는 중이라 학습자와 함께 큰다(설계 §8-1).
  - 말투는 **친근한 해요체에 반말을 조금 섞는다**: 「봐요, 물건 40가지가 한 줄씩 나왔잖아!」, 「두근두근… 사실 나도 떨려요.」
  - **혼내지 않는다.** 오류는 「단서」, 틀린 답에는 무엇이 다른지만 말한다. 「틀렸다」보다 「이 카드가 빠졌어요」.
  - 칭찬은 구체적으로 한다(「order_items와 헷갈리지 않았네요!」).
- 용어(한 번 정하면 바꾸지 않음): 표(장부), **행**(가로 한 줄), **열**(세로 한 줄), SQL 낱말, 결과 표, 조립, 카드, 오류(= 단서), 엽전(값의 단위).
- **「빈칸」은 NULL만 뜻한다(판정 R35).** 6장 제목이 「빈칸 다루기」이고 2~5장도 「재고 칸이 빈(NULL) 물건」, 「빈칸은 6장에서」로 써 왔다.
  - blank 문제에서 칩을 채워 넣는 자리는 **「빈자리」**라 부른다: 「…나오게 빈자리를 채워 보세요」, 화면 이름표 「빈자리에 넣을 조각」(`src/ui/lesson.js`).
  - 문제·해설·말풍선·틀·화면 글 어디서도 칩 자리를 「빈칸」이라 쓰지 않는다. 띄어쓰기 칸은 「띄어쓰기」·「공백」이라 쓴다.
- **엔진마다 다른 동작은 「이 장터에서는」을 붙인다(판정 R36).** 데이터베이스마다 결과가 다른 것을 모든 SQL의 규칙처럼 쓰지 않는다. 카드·문제·보기·해설·요약 모두 같다.
  - 1~5장의 예: 정수 나누기의 소수점 버림(2-4), 별칭 없는 계산 열의 이름이 쓴 식 그대로인 것(2-2), 따옴표 안 글자 값의 대소문자 구별(3-3, MySQL 기본 설정에서는 `'Abc' = 'abc'`가 참), `=!`가 오류인 것(3-4, MySQL은 `= !…`로 읽음), 날짜가 글자 값인 것(이 장터의 저장 방식).
  - 6~13장의 예: 묶지 않은 열을 SELECT에 놓기(`SELECT name, COUNT(*) … GROUP BY shop_id`, SQLite만 받음 → 「많은 데이터베이스에서 오류라 쓰지 않는다」로만, 7·8장), HAVING에서 SELECT 별칭 부르기(`HAVING n >= 9`, PostgreSQL은 오류 → HAVING에는 셈을 다시 적는다, 8장), 값 자리 서브쿼리가 여러 행을 냄(PostgreSQL·MySQL은 오류, 이 장터는 오류 없이 한 값만 씀 → 그런 SQL은 보이지 않고 말로만, 12장), WITH의 앞 중간 표가 뒤 중간 표 읽기(이 장터 SQLite는 받고 많은 데이터베이스는 오류 → 「많은 데이터베이스는 앞 표가 뒤 표를 못 읽어요. 이 장터에서는 되지만 늘 쓰는 차례대로 적어요」, 13장), 셈 안에 셈 `AVG(COUNT(*))`(Oracle 등은 받음 → 「이 장터를 비롯한 많은 데이터베이스에서는」, 13장).
  - 모든 데이터베이스에서 같은 것(SQL 낱말의 대소문자 무시, NULL과의 셈·비교, `BETWEEN`의 양 끝 포함, 띄어쓰기가 다른 글자 값)은 붙이지 않는다.
- **값은 「N엽전」으로 쓴다**(판정 R31): 「12엽전」, 「100엽전 넘는 물건」.
  - 설계 §6 표의 「엽전 100냥 넘는 물건」 같은 「냥」은 쓰지 않는다. 용어집과 `data/schema.js`(`price` = 값(엽전))를 따른다.
  - 3장 장터 예도 「100엽전 넘는 물건」으로 쓴다.
  - 표·열 이름은 영어 그대로 쓰고, 처음 나올 때 한글 뜻을 붙인다: 「shops(가게)」, 「price(값)」.
  - 값(가게 이름·손님 이름·마을)은 한글이다.
- **조사**: 레슨 글은 손으로 쓰니 SQL 낱말을 읽는 소리에 맞춘다.
  - 받침 있음 → 「을/이/은」: `FROM`(프롬)·`JOIN`(조인)·`LIMIT`(리밋)·`HAVING`(해빙)·`NULL`(널)·`IN`·`ON`·`BETWEEN`·`UNION`·`NOT`.
  - 받침 없음 → 「를/가/는」: `SELECT`(셀렉트)·`WHERE`(웨어)·`AND`·`OR`·`LIKE`·`ORDER BY`·`GROUP BY`·`COUNT`·`CASE`·`WITH`·`OVER`·`RANK`(랭크)·`LAG`·`LEAD`·`*`(별표).
  - 앱이 조사를 붙이는 곳(`need` 안내 등)은 `src/shuffle.js`의 `sqlEul`·`eul`이 같은 규칙으로 고른다. 틀의 `{자리 표시}` 뒤에는 조사를 붙이지 않는다(6절).
- **도깨비 민속 이야기는 지어내지 않는다.** 앱 설정(장터, 두억이, 손님 종류 `도깨비·사람·여우`)만 쓴다. 「도깨비는 ○○를 좋아한다」 같은 민속 사실을 쓰고 싶으면 넣지 말고 보고서에 적는다. 출처 확인은 작업 17이 한다(설계 §5-3).
- 문장·문제·데이터는 모두 새로 쓴다. 데이터 참고 저장소(`cybergeekgyan/SQL-for-Data-Scientists`, `krishnaik06/…`)의 문장·문제를 옮기지 않고, 앞 저장소의 PDF는 열지 않는다(설계 §6).
- 실존 인물·특정 종교를 비하하지 않는다.

### 13-2. 첫 카드와 A3 「의뢰」

- **첫 카드 `say`는 방금 끝낸 장과 잇는 한 줄로 시작한다**: 「N장에서 ○○를 배웠죠? 오늘은 한 걸음 더」 꼴. 예: 「4장에서 NOT으로 조건을 뒤집었죠? 오늘은 괄호째 뒤집어 봐요.」
- **A1·A2**는 그 장 주제를 한 걸음 더 깊게 한다. 뒷장 문법을 미리 쓰지 않는다(설계 A4).
- **A3는 「의뢰」**다: 두억이가 장터에서 받은 부탁으로 시작한다(「구름 잡화점 최보부 님이 의뢰를 맡겼어요: …」처럼, 가게·주인·손님 이름은 `data/market.sql`에 있는 것만). 그 장 문법 + 그 장 심화 낱말로 풀린다. 숫자·이름은 실제로 돌려 확인한 것만 쓴다.
- **A3는 A1·A2를 했다고 기대하지 않는다**(순서 없음). A3가 A1·A2의 모양(괄호 셈 차례, `%`, 주석, NULLIF 등)을 쓰면 A3 카드에서 한 번 다시 보여 준다(4절 「카드에서 처음 보여 주고 문제는 그 뒤」).

### 13-3. 심화 전용 낱말 (`ADVANCED_GRAMMAR`, 확정)

N장 심화 레슨이 쓸 수 있는 것 = **1~N장 본 과정 낱말(`GRAMMAR`) + N장 심화 전용 낱말**.

| 장 | 심화 전용 | 모양만(새 낱말 없음) |
|---|---|---|
| 1 | 주석 `--` | FROM 없는 `SELECT 40`(숫자 값만 — 글자 값 `'…'`은 3장, `+ - * /`·쉼표 열 목록은 2장이라 쓰지 않음, 판정 R52) |
| 2 | 나머지 `%` | 괄호로 셈 차례 묶기 |
| 3 | 없음 | 열끼리 비교 `stock < price`, 날짜 글자 비교 `opened_on < '2026-01-03'` |
| 4 | 없음 | `NOT ( … )`, LIKE `_`·`%` 섞은 무늬 |
| 5 | 없음 | ORDER BY 식·별칭, `LIMIT k OFFSET k×(n−1)` 쪽 나누기(OFFSET은 5장 본 과정 낱말) |
| 6 | `NULLIF` | WHERE·ORDER BY 안 `COALESCE` |

- **앞 장 심화 낱말은 이어지지 않는다(판정 R53)**: `--`는 1장 심화에서만, `%`는 2장 심화에서만 된다. 2장 심화를 건너뛴 학습자도 3장 심화를 열기 때문이다.
- **본 과정 레슨·매일 도전 틀에는 심화 전용 낱말을 쓰지 못한다.** 점검기가 「심화 전용 낱말: %(2장 심화) — 본 과정 레슨·매일 도전 틀에서는 쓰지 않음」으로 잡는다.
- **조립 카드 크기(판정 R51)**: 1~5장 **심화** 조립은 1~3토큰 구절 카드(30칸 안)를 쓸 수 있다. 예: `price % 2`, `stock < price`, `LIMIT 5`, `OFFSET 5`, `NOT (`, `AS remainder`. 괄호·쉼표도 한 토큰으로 센다(`(price + 2)`는 5토큰이라 `(`·`price + 2`·`)`로 나눔). `SELECT`·`FROM`·`WHERE`·`ORDER BY`는 지금처럼 한 장씩 둔다(손으로 지킴). **본 과정** 1~5장은 그대로 카드 하나에 낱말 하나다. 6장 심화는 본 과정 6장과 같다(R38).
- 블록 주석 `/* */`은 어디서도 쓰지 않는다(점검기가 막음).

### 13-4. 주석 카드 (1장 심화)

- 주석 카드는 `"-- 가게 장부"`처럼 한 장, 조각 하나로 센다. 앱(`cardsToSql`)은 주석 카드 뒤를 줄바꿈으로 이어 뒤 카드가 주석에 삼켜지지 않는다.
- **조립 정답에 넣은 주석 카드는 반드시 `need`에 적는다.** 주석은 빼도 결과가 같아서, `need`가 없으면 점검기 `drop-one`이 「쓸모없는 카드」로 잡는다. 과제 문장에도 「메모를 달아」처럼 주석을 쓰라고 적는다.
- **글자 보기(설명 글 보기) 안의 `--`는 점검기가 SQL로 보지 않는다.** 그래서 주석이 든 SQL을 글자 보기로 내지 않는다(검사를 피해 가게 됨). 주석 SQL은 카드 `sql`, 문제 `code`, `{ sql }` 보기, 빈자리·줄 놓기·조립에만 둔다.

### 13-5. 엔진 차이 (「이 장터에서는」, R36)

심화는 엔진마다 다른 곳을 자주 건드린다. 모두 「이 장터에서는 …, 다른 데이터베이스는 …일 수 있어요」로 감싼다.

- FROM 없는 SELECT(1-A1): FROM을 꼭 달아야 하는 데이터베이스도 있다.
- 주석(1-A2): `--` 뒤에 띄어쓰기를 꼭 두어야 하는 데이터베이스가 있어 늘 한 칸 띄운다.
- `%`(2-A2): 음수의 나머지 부호, `MOD()` 함수 이름은 데이터베이스마다 다르다(장터 값에는 음수가 없으니 말로만).
- 정수 나누기(2-A3): 2-4 그대로 「이 장터에서는 소수점 아래를 버려요」.
- 한글 글자 비교(3-A2): 가나다 차례는 데이터베이스·설정에 따라 다를 수 있다. 날짜 글자(`'2026-01-03'`)의 비교는 그대로 날짜 차례다.
- 0으로 나누기(6-A2): 이 장터에서는 빈칸(NULL)이 나오고, 오류를 내는 데이터베이스도 있다.
- 빈칸의 줄 세우기 자리(5-A1·6-A1): 6-3과 같다. 5장 심화는 빈칸이 없는 행만 세우도록 조건을 고른다.

### 13-6. 주제 바꾸기 규칙 (설계 §2)
